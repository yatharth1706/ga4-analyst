  Verdict on the spec

  The scope is well controlled and the priorities are in the right order. The
  weak spots are the specific places where bugs will appear and where the
  interviewers will push: how charts get their data, how SQL is kept safe, how
  the loop stops, what the data actually means, and how you show the answers are
  correct. Here's what I'd change.

  Changes I'd make

  1. Charts should point at query results, not carry numbers.
  In §10 the chart spec ({type, x, y}) has no data source. If the model copies
  the data into JSON, it can make up numbers and you pay for the extra tokens.
  Instead, give each successful query a query_id. A chart then says {query_id, 
  type, x, y, series?, title}, and the backend fills in the real rows. That way
  a chart can't show a number BigQuery didn't return.

  2. Make charts a tool call and keep the narrative as plain text.
  Don't make the final answer JSON. Add a create_chart tool. The backend checks
  that the columns exist in that query's result and that the chart type is
  allowed. If the check fails, the model gets the error back and fixes it inside
  the loop. The final message is ordinary markdown, so it can stream and
  there's no JSON to fail parsing.

  3. Replace the keyword blocklist in §7 with BigQuery's own checks.
  A regex for DELETE/DROP blocks harmless queries, such as a string literal
  containing "update", and misses edge cases. I'd stack these checks instead:
  - A dry run first. BigQuery reports the statement type, and we reject anything
    that isn't SELECT (multi-statement scripts come back as SCRIPT). The dry
    run also tells us how many bytes the query will scan.
  - maximum_bytes_billed set on every job.
  - A job timeout and a cap on returned rows.
  - A service account with only Data Viewer and Job User roles, so writes fail
    at the permission level anyway.

  4. The loop in §5 needs details the pseudocode leaves out.
  The pseudocode handles one tool call and never stops. It also needs:
  - Parallel tool calls: Claude can request several tools in one turn, and all
    their results must go back in a single message.
  - A cap of about 10 iterations, then one last call without tools that forces a
    summary.
  - stop_reason handling, including max_tokens.
  - Tool exceptions returned as is_error results instead of crashing the
    request.
  - Small results for the model: at most about 100 rows, plus the total row
    count and a "truncated" flag. The full result stays on the server for charts
    and tables.

  5. Curated dataset notes are worth more than a get_schema tool.
  Dumping the raw GA4 schema is long and leaves out the parts that cause wrong
  answers. I'd put a hand-written dataset guide in the system prompt (prompt
  caching keeps it cheap) covering:
  - The data runs from 2020-11-01 to 2021-01-31. "December" means Dec 2020, and
    "last month" means Jan 2021. Filter dates with _TABLE_SUFFIX to scan less.
  - Two kinds of revenue: order revenue (ecommerce.purchase_revenue_in_usd) and
    item revenue (items.item_revenue_in_usd). Summing order revenue after
    UNNEST(items) counts it more than once, which is the classic bug.
  - traffic_source.* is the source that first brought the user, not the 
    session's source. So the answer to "which source drove revenue" needs that
    caveat.
  - Sessions are identified by user_pseudo_id plus ga_session_id, and the
    standard pattern for unnesting event_params.
  - Placeholder values from Google's anonymising of the data, such as <Other>
    and (data deleted).

  That leaves two tools: run_sql and create_chart. I'll check every claim above
  against the real data on day one.

  6. Show the work (missing from the spec).
  Each answer should have a collapsible list of steps: the SQL, how long it
  took, bytes scanned, row count, and the data table. For an analytics product
  this is how users come to trust the numbers, and it's how reviewers will judge
  correctness.

  7. Stream progress with server-sent events (SSE) from the start.
  §18 leaves this optional. The loop already produces separate events (query
  started, result, chart, text, done, error), so streaming them is about an hour
  of work. That's what makes the app feel like an agent at work rather than a
  spinner. Streaming the narrative word by word is optional.

  8. Tighten the clarification rule in §16.
  "Ask when ambiguous" tends to make the assistant ask too many questions. My
  rule: ask when it's unclear what to analyse ("What performed best?"). When
  only the metric is unclear ("top products"), assume revenue, say so in one
  line, and offer alternatives.

  9. Prove correctness with a golden question set, not API tests.
  Write 10–15 questions with hand-checked SQL and expected answers, and a script
  that runs the agent and compares the key numbers. That proves correctness
  better than mocked API tests, and it's a strong thing to talk about in the
  interview. Keep the unit tests for the SQL guard and for the loop, using a
  fake LLM that replays scripted responses (multiple tools, error recovery,
  iteration cap).

  10. Decide where conversation state lives (§12 doesn't say).
  - Storage: an in-memory map from conversation_id to the full message list,
    tool calls included, plus the stored query results. It's lost on restart,
    which is documented.
  - Trimming: older tool results shrink to their SQL plus a summary, so the
    context doesn't grow without limit.
  - One request at a time: each conversation handles one request at a time.

  11. Protect the deployed link.
  Without login, anyone with the URL can spend your API credit. A per-IP rate
  limit plus a daily cap, or a shared access code, takes about 20 minutes.

  12. Small items:
  - Cache query results by SQL hash, so demos and eval runs are fast and cheap.
  - Convert BigQuery NUMERIC and date values to plain JSON numbers and strings.
  - Set the BigQuery location to US.
  - Drop pie charts; keep line, bar, KPI card and table.

⏺ React + Vite plus FastAPI is a good choice. Vercel can host both in one
  project, with one catch about where conversation history lives. And not all of
  changes 1–12 are worth doing: some save time, some are essential, and a few
  should be cut.

  Is React + Vite the fastest?

  Yes, for this app. It's a single-page chat with no SEO and no server-rendered
  pages. Next.js would add server concepts we don't need, since FastAPI is the
  backend. With Vite, npm run dev proxies /api to uvicorn and you're running.
  For charts I'd use Recharts, which is React-native and covers bar, line and
  KPI card. For the narrative text I'd use react-markdown.

  Deployment: yes, one Vercel project works

  Vercel now runs FastAPI natively, alongside a static Vite build, in one
  project. Streaming responses work, and functions can run for up to 300s by
  default, which is plenty for an agent loop.

  The catch: Vercel functions don't share memory reliably between requests, so
  storing conversations in server memory (change #10) won't work there. I'd make
  the backend stateless:
  - Within one question: the full Gemini tool-calling transcript lives in memory
    only for the duration of that request.
  - Across questions: the browser keeps a compact history (each question, the
    SQL that ran, a small result preview, and the answer) and sends it with
    every request. That's enough context for "what about December?".

  This also solves the problem of the context growing too large, with no
  database and no server state. It's a solid design to defend in the interview.

  GCP credentials:
  - Locally, run gcloud auth application-default login.
  - On Vercel, the service-account JSON goes into an environment variable.
  - The BigQuery sandbox doesn't need billing enabled.

  Gemini: one thing to watch

  The google-genai Python SDK has automatic function calling. If you pass it
  Python functions as tools, the SDK runs the loop for you, which would break
  the "write the loop yourself" rule. We'll pass plain function declarations,
  switch that feature off explicitly, and run the loop ourselves.

  We'll also append the model's response content to the history unchanged,
  because Gemini expects some hidden data in it (thought signatures) to come
  back on the next call. I'll keep all Gemini-specific code in one module, so
  switching to Claude later is a single-file change if Mary asks for it. The
  model name will be an environment variable; I'll list the models your key can
  use at setup and start with a Flash model, moving up to Pro if the test
  questions show weak SQL.

⏺ You're allowed to use the google-genai SDK, but I've written the spec to call
  Gemini over raw HTTP instead.

  Why raw HTTP: The rule allows "a vendor SDK's messages endpoint", and the
  SDK's generate_content call is exactly that. But the same SDK has automatic 
  function calling: give it Python functions and it runs the tool loop for you,
  which is the part the assignment asks us to build ourselves. We could switch
  that off, but then a reviewer reading the code has to trust that we did.
  Calling generateContent directly with httpx removes the question, costs about
  the same amount of code (~80 lines with retries), and keeps every request and
  response visible for debugging and for walking through the code in the
  interview. All Gemini code is in one module, so we can swap the SDK back in,
  or switch to Claude, by changing one file.

  Spec updated. spec.md is now v2 with everything we agreed. I saved your
  original draft as spec.original.md because the folder isn't a git repo yet.
  What's new compared with your draft:
  - Stateless backend: the browser keeps a short history of each turn (question,
    SQL, small result preview, answer) and sends it with every request. This
    works on Vercel and keeps follow-up context small.
  - SQL safety: a BigQuery dry run checks the statement type, and a byte cap
    limits what any query can scan.
  - Two tools only: run_sql, and create_chart, which points at a query result

  - Agent loop rules: several tool calls in one turn, an iteration cap of 10,

  - GA4 dataset notes: the dataset knowledge goes into the prompt, marked to be

    of double-counting revenue, and traffic_source describing how the user was

  - Live progress: each step streams to the screen as it happens.
  - Testing: unit tests for the SQL guard and the agent loop, plus about 8

  4. What the app does with a question

  It works like a junior data analyst you can chat with:

  You ask:      "Which device brings more revenue?"
     ↓
  AI decides:   "I need revenue grouped by device" → writes a SQL query
     ↓
  BigQuery:     runs the query on the real data → returns a small table
     ↓
  AI checks:    "Is this enough? Did the query fail?" → maybe runs another query
     ↓
  You see:      a chart + a short explanation + the SQL it used

  That loop, where the AI decides, runs a query, looks at the result and decides
  again, is the agentic loop. It's the heart of the assignment, and the part we
  write ourselves.

  5. Why I mentioned all those "quirks"

  Google scrambled some of the data for privacy. Some values are replaced with
  placeholders like <Other> or (data deleted), and some fields behave oddly. If
  the AI doesn't know this, it gives answers that look confident but are wrong.

  So I wrote the AI a cheat sheet (ga4_notes.md) that it reads before every
  question. You don't need to memorise the details. That file holds them for
  you.

❯ why google app cred leak and gcp does not leak ?                              

⏺ Neither variable leaks by itself. What matters is what the code does with the
  value when something goes wrong.

  GOOGLE_APPLICATION_CREDENTIALS is meant to hold a file path, like
  /Users/you/.config/hockeystack/ga4-analyst.json. The path isn't secret; the
  file it points to is. Google's library reads this variable on its own and
  opens that file. If the file isn't there, it raises an error saying so:

  File <whatever is in the variable> was not found.

  That's reasonable when the variable holds a path. But you'd put the key itself
  in it, so Google's library printed the whole key into the error, and the
  error went into the Vercel logs.

  GCP_SERVICE_ACCOUNT_JSON is our own variable, meant to hold the key's 
  contents. Only our code reads it (client.py): it parses the JSON and gives it
  straight to Google as credentials. Nothing in that path puts the value into an
  error message or a log line. If the JSON were broken, the error would be
  something like "Expecting value: line 1 column 1", which describes the problem
  without showing the content.

  Why we need two variables at all:
  - On your Mac, the key is a file on disk, so the standard "path to a file"
    variable works.
  - On Vercel, there's no file, only environment variables. So we store the
    key's contents in an environment variable, and our code reads it as
    contents, not as a path.

  The general lesson: a secret is only safe in code that treats it as a secret.
  Any value can end up in an error message if the code that reads it echoes it
  back. The 3-line check I offered would make the backend stop with
  "GOOGLE_APPLICATION_CREDENTIALS should be a file path; use
  GCP_SERVICE_ACCOUNT_JSON for the key contents" if anyone repeats this mistake,
  before Google's library can print the key.

  ## Key decisions                                                              
                                                                                
  - **A hand-written loop over raw HTTP, no SDK.** Gemini's SDK can run tool    
  calls automatically, which is the part the task asks us to write. Raw         
  requests make that unambiguous and keep every request and response visible.   
  - **SQL safety from BigQuery itself, not a regex.** A dry run must report a   
  single `SELECT` scanning under 3 GB before anything runs; the real job also   
  has a billing cap, a timeout and a row limit. The service account can only    
  run queries.                                                                  
  - **Charts point at a query's result and carry no data of their own.** The    
  backend validates each chart spec and attaches the real rows, so a chart      
  can't show a number BigQuery didn't return. A bad spec goes back to the model 
  to fix.                                                                       
  - **A curated dataset guide in the prompt, instead of a "read the schema"     
  tool.** The traps below aren't visible in a schema. Every fact in the guide   
  was checked against the data.                                                 
  - **A stateless backend.** The browser sends a compact history (question,     
  answer, SQL, a few preview rows) with each question. That works on serverless 
  hosting, and the client can't forge tool results.                             
  - **Streaming progress events instead of a spinner.** Answers take 20–45 s,   
  so the user watches each query start and finish.                              
  - **Four row caps, on purpose.** BigQuery fetches 500 rows for the table and  
  charts (`MAX_ROWS`). The model only sees 100 (`MODEL_MAX_ROWS`) so it         
  aggregates in SQL instead of paging. History keeps 10 preview rows per query  
  (`PREVIEW_ROWS`). Bar charts are rejected above 50 rows (`MAX_BAR_ROWS`).     
  - **`gemini-3.8-flash`.** Three models gave identical answers on the test     
  questions; Flash was the fastest.
